PerfRouter — Technical Reference

Benchmark-driven LLM routing using XGBoost and sentence-BERT. Routes incoming queries to the model with the highest predicted utility (quality − α × cost) with no LLM call at inference time.

XGBoost sentence-BERT 50–80 models 33 task types 46 features 10-fold CV

1System overview

PerfRouter answers the question: "Given this query, which model in the pool has the best predicted quality adjusted for cost?"

It differs from embedding-based routers (TRouter) in that it does not route on query semantics alone. Instead it:

  1. Classifies the query into one of 33 task types using cosine similarity against pre-computed sentence-BERT embeddings — no LLM call.
  2. For each model, predicts its quality on that task type using XGBoost — trained on benchmark-derived feature vectors and optional WCB ground truth.
  3. Applies a cost penalty: $ \hat{u}_m = \hat{q}_m - \alpha \cdot \tilde{c}_m $ and routes to the model with the highest adjusted utility.

Why not a neural router?

With 50–80 models × 33 task types = 1,650–2,640 training rows, XGBoost is the right fit. It handles small-to-medium datasets naturally via built-in L1/L2 regularisation, deals with missing features natively (NaN), and produces feature importances for interpretability.

Why sentence-BERT for classification?

The 33 task type definitions are embedded once at startup. At inference time, a single dot product against pre-normalised embeddings gives cosine similarity in ~1 ms — no API call, no latency overhead, no cost.

3Feature vector — 46 features per model

Each row in model_features.csv represents one model. The feature vector has four groups:

A — Task-type affinity (33)
  • One score per task type
  • Weighted avg of benchmark scores
  • NaN if no benchmark data
  • Only one column active per training row
B — Structural (9)
  • total_params_B
  • active_params_B
  • moe_density
  • context_window_k
  • effective_context_k
  • context_headroom_ratio
  • speed_output_tps
  • latency_ttft_s
  • price_blended_per_1M *
C — Boolean flags (5)
  • flag_reasoning (0/1)
  • flag_thinking (0/1)
  • flag_vision (0/1)
  • flag_tools (0/1)
  • flag_free (0/1)
D — WCB seed (3, optional)
  • wcb_avg_score
  • wcb_avg_score_nonzero
  • wcb_zero_rate
  • NaN for models not run on WCB
* Pricing excluded from XGBoost inputs. price_blended_per_1M (and input/output/cache prices) are listed in group B but are excluded from the XGBoost feature matrix at training time. Cost is applied explicitly at inference as $\hat{u}_m = \hat{q}_m - \alpha \cdot \tilde{c}_m$. Including cost in XGBoost would cause it to double-count the cost signal.

Blended cost formula

AA convention: 3 input tokens per 1 output token (3:1 ratio).

Blended cost ($/1M tokens)
$$c_m = \frac{3 \cdot p^{\text{in}}_m + p^{\text{out}}_m}{4}$$

MoE density

Mixture-of-Experts activation density
$$\rho_m = \frac{\text{active\_params\_B}_m}{\text{total\_params\_B}_m}$$

Dense models: $\rho = 1.0$.   MoE models: $\rho < 1.0$. E.g. DeepSeek-V4-Pro: 49B active / 1600B total → $\rho = 0.031$.

4Affinity score formula

The affinity score $a_{m,t}$ measures how well model $m$ is suited to task type $t$, derived entirely from AA and Arena benchmark scores.

Task-type affinity score
$$a_{m,t} = \frac{\displaystyle\sum_{b \in \mathcal{B}} w_{t,b} \cdot s_{m,b}} {\displaystyle\sum_{b \in \mathcal{B} \,:\, s_{m,b} \neq \text{null}} w_{t,b}}$$

where $w_{t,b} \in W$ is the weight of benchmark $b$ for task type $t$, and $s_{m,b}$ is the model's score on benchmark $b$. The denominator re-normalises over benchmarks where the model has data, so missing scores are skipped rather than treated as zero.

Benchmark score normalisation

Scores are normalised to [0, 1] before the weighted sum:

AA index normalisation
$$\tilde{s}_{m,b} = \begin{cases} s_{m,b} / 100 & \text{if } b \in \{\texttt{aa\_intelligence\_index, aa\_coding\_index, aa\_math\_index}\} \\ s_{m,b} & \text{otherwise (already in } [0,1]\text{)} \end{cases}$$

Arena ELO normalisation

Raw ELO is on an arbitrary scale (~1000–1600). Per-category min-max normalisation maps it to [0, 1] across the leaderboard:

Arena ELO → [0, 1]
$$\tilde{e}_{m,c} = \frac{\text{ELO}_{m,c} - \min_k \text{ELO}_{k,c}} {\max_k \text{ELO}_{k,c} - \min_k \text{ELO}_{k,c}}$$

Categories: text, search, code, vision, document. Computed separately per category. Used as the benchmark score for task types that have no adequate AA coverage.

Benchmark weight matrix $W$

$W \in \mathbb{R}^{33 \times |\mathcal{B}|}$ is generated by the LLM in build_task_taxonomy.py and stored in benchmark_weights.json. Each row sums to 1.0. The Arena patch (Step 3) overwrites specific rows for subjective task types.

Feature masking — making XGBoost task-type-aware

A single XGBoost model is trained across all 33 task types. Without intervention it would learn a global ranking ("model X is always best") and ignore task-type variation.

The fix: for each training row, all affinity columns are masked to NaN except the one corresponding to that row's task type:

Feature masking per training row $(m, t)$
$$x_{m,t}^{(b)} = \begin{cases} a_{m,t} & \text{if } b = \texttt{affinity\_}t \\ \text{NaN} & \text{if } b \text{ is any other affinity column} \\ f_{m,b} & \text{otherwise (structural / flag / WCB columns)} \end{cases}$$

XGBoost's tree_method="hist" handles NaN natively by learning which branch direction minimises loss for missing values. At inference time, the same masking is applied — only the active task type's affinity column is populated.

Label normalisation (within task type)

Per-task-type min-max normalisation of labels
$$\tilde{y}_{m,t} = \begin{cases} \dfrac{y_{m,t} - \min_k y_{k,t}}{\max_k y_{k,t} - \min_k y_{k,t}} & \text{if } \max_k y_{k,t} - \min_k y_{k,t} > 0.01 \\[10pt] 0.5 & \text{otherwise (all models equal on this task type)} \end{cases}$$

6Cross-validation

10-fold stratified cross-validation is run automatically at the start of Step 6, before final model training. It is the primary signal for assessing generalisation — in-sample metrics (§5) are optimistic by design.

CV is for evaluation only. The deployed perf_router.pkl is always trained on all data. This maximises coverage of model × task combinations in the final model while using CV to detect overfitting without withholding any training signal.

Stratified split strategy

Folds are stratified by task_type — every fold is guaranteed to contain rows from all 33 task types. Without stratification, a fold missing a task type would produce meaningless out-of-fold predictions for that type, since the model would never have seen it during training.

Stratified K-Fold split
$$\text{StratifiedKFold}(k=10,\; \text{stratify}=\text{task\_type},\; \text{shuffle}=\text{True},\; \text{seed}=42)$$

With 50–80 models × 33 task types ≈ 1,650–2,640 rows, each fold contains ~165–264 rows. The same XGBoost hyperparameters and sample weights are used in every fold as in the final fit.

Metrics reported per fold

Metric Formula What it measures
MAE $\frac{1}{n}\sum|y_i - \hat{y}_i|$ Average absolute prediction error on held-out rows
RMSE $\sqrt{\frac{1}{n}\sum(y_i - \hat{y}_i)^2}$ Penalises large errors more heavily than MAE
R² $1 - \frac{\text{Var}(\text{residuals})}{\text{Var}(y)}$ Fraction of label variance explained by the model
Routing accuracy $\frac{1}{|\mathcal{T}_{\text{fold}}|}\sum_{t} \mathbf{1}[\arg\max_m \hat{q}_{m,t} = \arg\max_m q_{m,t}]$ For each task type in the fold, does the predicted best model match the actual best model? This is the metric routing correctness depends on.
OOF R² $R^2$ over all out-of-fold predictions simultaneously More robust than mean of per-fold R² values — computed once at the end across all held-out predictions pooled together

Routing accuracy — the primary routing metric

Standard regression metrics (MAE, R²) measure prediction accuracy over individual rows. But PerfRouter doesn't need to predict exact scores — it needs to correctly rank models within each task type. Routing accuracy measures this directly:

Routing accuracy per fold
$$\text{RoutingAcc} = \frac{1}{|\mathcal{T}_{\text{fold}}|} \sum_{t \in \mathcal{T}_{\text{fold}}} \mathbf{1}\!\left[\underset{m}{\arg\max}\;\hat{q}_{m,t} = \underset{m}{\arg\max}\;q_{m,t}\right]$$

Only task types with ≥ 2 models in the validation fold are counted (can't measure ranking with a single model). Reported as a percentage.

Automatic fold reduction guard

If the smallest task type has fewer rows than the number of folds, StratifiedKFold would crash. The training script automatically reduces fold count to min(k, min_task_type_count) and prints a warning. This can happen when the pool is small or a task type has sparse benchmark coverage.

7Inference & routing

All heavy state (XGBoost model, task embeddings, registry, features) is loaded once at startup. Each route() call is ~2–4 ms.

Step 1 — Task type classification (sentence-BERT)

Each of the 33 task types has a definition + examples embedded at startup using all-MiniLM-L6-v2 (384-dim). At inference:

Cosine similarity (L2-normalised embeddings → dot product)
$$\text{sim}(q, t) = \mathbf{e}_q \cdot \mathbf{e}_t \qquad \text{where } \|\mathbf{e}_q\|_2 = \|\mathbf{e}_t\|_2 = 1$$

Top-$k$ task types are selected ($k = 3$ by default) and used as a similarity-weighted ensemble:

Ambiguity fallback condition
$$\text{if } \max_t \,\text{sim}(q, t) < \theta_{\min} \;\Rightarrow\; \text{route to cheapest eligible model}$$

Default $\theta_{\min} = 0.20$. Configurable via PERF_ROUTER_MIN_SIMILARITY.

Step 2 — Quality prediction (XGBoost)

Similarity-weighted quality prediction
$$\hat{q}_m = \sum_{t \in \text{top-}k} \frac{\text{sim}(q,t)}{\sum_{t'} \text{sim}(q,t')} \cdot f_{\theta}(\mathbf{x}_{m,t})$$

$f_\theta$ is the trained XGBoost regressor. $\mathbf{x}_{m,t}$ is the masked feature vector for model $m$, task type $t$ (same masking as training time).

Step 3 — Adjusted utility & routing decision

Cost normalisation (across pool)
$$\tilde{c}_m = \frac{c_m}{\max_k c_k}$$
Adjusted utility
$$\hat{u}_m = \hat{q}_m - \alpha \cdot \tilde{c}_m$$

$\alpha$ (default 0.3) is configurable at runtime without retraining. $\alpha = 0$ → quality only. $\alpha = 1$ → full cost penalisation.

Routing decision (standard mode)
$$m^* = \underset{m \in \mathcal{E}}{\arg\max} \;\hat{u}_m$$

$\mathcal{E}$ = eligible model set (after context window, vision, and cost-cap filtering).

Degradation threshold mode

Quality floor
$$q^{\text{floor}} = \hat{q}_{m^*_\text{quality}} \cdot (1 - \delta)$$
Degradation-threshold routing
$$m^* = \underset{m \in \mathcal{E} \,:\, \hat{q}_m \geq q^{\text{floor}}}{\arg\min} \; c_m$$

Default $\delta = 0.0$ (disabled). Set $\delta = 0.10$ to accept up to 10% quality drop for a cheaper model.

Routing modes

normal
Condition: query non-empty, $\max \text{sim} \geq \theta_{\min}$
Full XGBoost prediction + cost adjustment. Routes to $\arg\max \hat{u}_m$.
fallback_ambiguous
Condition: $\max \text{sim} < \theta_{\min}$
Classifier is uncertain. Skip XGBoost. Route to cheapest eligible model.
fallback_empty
Condition: query is empty/null
No text to embed. Route to cheapest eligible model.

Eligibility filters (applied before routing)

FilterConditionRelaxed if all models filtered?

All parameters below are read at startup and apply without retraining.

Adding a new model

# 1. Add entry to models.yaml (or let discover_models.py auto-populate)
# 2. Re-run pipeline from step 1 (fetches AA data, rebuilds features, retrains + CV)
uv run perf-pipeline --force-step 1

# 3. (Optional) Run WCB on the new model and add its results to
#    data/wcb_training_labeled.csv, then retrain from step 6 only:
uv run perf-pipeline --force-step 6 --wcb-csv data/wcb_training_labeled.csv

# 4. For a quick retrain without waiting for CV (e.g. during development):
uv run perf-pipeline --force-step 6 --wcb-csv data/wcb_training_labeled.csv --no-cv
